# The preprocessor

**Status:** implemented and wired into the front end. This document is the
contract for `src/pp`, the way [`lexer.md`](lexer.md) is for `src/lex` and
[`parser.md`](parser.md) is for `src/parse` + `src/syntax`.

Written before the code on purpose: the decisions below are the
expensive-to-change ones, and one of them -- provenance -- is impossible to
retrofit. Two of them were *checked* against the code as it was wired in, and
both had to be changed; see "What the implementation corrected" at the end.

## What it is

Translation phase 3 turns a file into preprocessing tokens; phase 4 is the
preprocessor: it evaluates `#`-directives, expands macros, and hands the parser a
single token stream that no longer has directives in it. Everything below the
parser that is not a token is the preprocessor's job.

`minc+` takes the C model, not the Rust or Swift one. C interop is the product's
reason to exist, which means `#include` and `#define` have to work on real
headers, and that means the semantics have to match the C standard and the
platform compilers exactly -- including the parts where the standard is subtle
and the parts where everyone disagrees. Being *better* than the market here does
not mean different macro semantics; it means:

- the same semantics, with **every failure mode bounded and named**;
- **provenance that survives expansion**, so a diagnostic (and later an editor)
  can say which macro, invoked where, through which includes;
- **the tooling information kept**, not dropped, because a preprocessor is also
  the thing that answers "where was this defined" and "what does this expand to".

The lexer's promise was losslessness; the parser's was a tree that still tiles
the bytes after an error. The preprocessor's is **totality under an adversarial
input**: it always terminates, always within a stated budget, and it always
produces a diagnostic when it stops -- never a hang, never a crash, never an
out-of-memory kill.

## The thing that decides everything: provenance

A preprocessor token can come from three places, and a good diagnostic says
which:

1. a macro **body**, in the header where the macro is defined;
2. a macro **argument**, at the invocation;
3. the **invocation point**, spliced in as `__LINE__`-like text.

Every compiler models this and every one of them does it differently, because
each has a 32-bit `SourceLocation` to pack it into. Clang packs a file id, an
offset and a macro-expansion bit into one 32-bit integer. GCC uses a base
location plus a virtual-location table, with a "spelling location" and an
"expansion location" -- two answers to two different questions, plus
`_cpp_builtin_macro` machinery for the third case. Both designs exist because
locations were already a packed integer when macro expansion was added.

`minc+` has no such constraint, so it takes the honest representation instead of
the compressed one:

```cpp
namespace minc::pp {

// Where a token was *written*: a real byte in a real file. This is what the
// caret points at, and it is never synthetic.
struct SourceLoc {
  support::FileId file = support::kInvalidFile;
  std::uint32_t offset = 0;
};

// Which macro invocations produced this token, innermost first.
using ExpansionId = std::uint32_t;
inline constexpr ExpansionId kNoExpansion = 0;

// A token's full origin: the bytes it was spelled with, and the chain of
// expansions it came out of.
struct TokenLoc {
  SourceLoc spelling;
  ExpansionId expansion = kNoExpansion;
};

} // namespace minc::pp
```

`kNoExpansion` means "written directly in this file". Anything else indexes an
append-only, hash-consed table:

```cpp
struct ExpansionFrame {
  SymId macro;          // the macro name, interned
  SourceLoc invocation; // where the invocation starts -- where the caret goes
                        // for "in expansion of macro 'X'"
  ExpansionId parent;   // the frame that contained the invocation
  SourceLoc define;     // where the macro was defined, for "defined here"
};
```

Frames are interned on `(macro, invocation, parent)`, the same way green tree
nodes are hash-consed, so the same macro invoked in a loop across two headers is
one frame and the table stays proportional to distinct invocation sites rather
than to expansion count. Three consequences, all of which are the point:

- **A diagnostic carries the whole chain.** `in expansion of macro 'MAX'` /
  `invoked here` / `included from 'a.h:3'` are notes generated by walking
  `parent` to `kNoExpansion`, bounded by a backtrace limit.
- **The chain is a value, not a string.** It can be rendered, compared, or sent
  over a protocol (an LSP wants the frames, not the prose).
- **`spelling` is always real text.** Every emitted token points at bytes that
  exist in some file; a formatter can lex that file and get the same token. When
  a token is *synthesized* (`#` and `##` are the only two ways), it records
  **both** operand spans and the paste operator's span, because "this identifier
  came from pasting `a` and `b`" is the only useful answer -- GCC and Clang both
  point at one of the two, which is a known annoyance.

Cost: a preprocessor token is `lex::Token` (12 bytes) plus a 16-byte `TokenLoc`
plus the table. The parser never sees the second half; it is dropped when the
stream is handed over, unless a client asked for it. This is the decision that
cannot be made later: if provenance is not threaded through the expander, the
only way to add it is to rewrite the expander.

## What the references do, and where they disagree

### GCC `cpplib` -- a context stack, and one token of pushback

`cpplib` is the reference implementation to read. It uses a **context stack**: a
linked list of `cpp_context`, where the top holds the unexpanded replacement
list of the innermost macro being expanded, or a macro argument during
pre-expansion, and `base context` reads straight from the lexer. A macro is
**disabled while its own replacement list is being scanned and re-enabled when
its context is popped** -- which is exactly the standard's wording ("the name of
the macro being replaced ... is not replaced"), expressed as stack state rather
than as a set attached to tokens.

Two details from their own documentation that a reimplementation gets wrong:

- **The order of "disable" and "look for `(`" matters.** `#define foo(x) bar x`
  then `foo(foo) (2)` expands to `bar foo (2)`: the inner `foo` does not expand
  even though the macro is enabled, because it has no following parenthesis
  *within the argument*, and it is then marked ineligible rather than re-tested.
  GCC documents that testing "is it disabled?" after finding the parenthesis is
  subtly wrong, because finding the parenthesis pops the context and
  re-enables the macro.
- **Their context stack is read-only after lexing, so "mark this token
  ineligible" is done by copying the token with a `NO_EXPAND` flag.** That mark
  is the standard's "no longer available for further replacement even if later
  re-examined", and it only ever matters for tokens that came out of argument
  pre-expansion.

The documented constraint that shapes their lexer -- *"backing up more than one
token when macros are involved is not permitted ... which is too hard"* -- is a
consequence of the design, not of the language. They work around it with
`funlike_invocation_p`, which remembers padding and pushes an extra context just
to hold it.

### Clang -- lexer-driven, with the expansion as a lexer

Clang's preprocessor is the **pull model**: the lexer produces a token on
demand, and the preprocessor asks for them, so nothing is materialized that
nobody reads. A macro expansion is implemented as a *lexer*: `TokenLexer` "returns
tokens from a macro body or token stream instead of lexing from a character
buffer", and text that has no source buffer to point at -- the spelling of a
pasted or stringified token -- is built in a `ScratchBuffer` that the lexer then
reads from. Expansion is therefore a stack of lexers, and the character-level
machinery (spelling, pasting) reuses the real lexer rather than a second
tokenizer.

Clang also keeps things a compiler normally throws away, and the tooling is
built on them:

- `PreprocessingRecord` / `PPCallbacks` record every macro definition,
  undefinition, inclusion and expansion with its source range -- which is what
  "go to definition" on a macro and "find all references to this macro" are
  made of. This is the single most transferable idea in their design for
  `minc+`, and it is why `src/pp` will keep a record.
- `MultipleIncludeOpt` detects the canonical include-guard pattern and, with
  `HeaderFileInfo`, remembers the guard macro so a re-include of that file is a
  **no-op that does not open the file at all** -- the "multiple-include
  optimization" that GCC, Clang and MSVC all implement.

### MSVC -- the conformance hazard

MSVC shipped a non-conforming preprocessor for decades (it is still the default
mode for older standards), which is why `/Zc:preprocessor` exists. The
visible differences are exactly the ones a macro library trips over: the new
preprocessor handles variadic macros and `__VA_OPT__` the standard way, while
the traditional one does not support `__VA_OPT__` at all, and the GNU
`, ## __VA_ARGS__` comma-deletion behavior is an extension, not standard. The lesson
for `minc+` is not "MSVC is wrong" but: **macro semantics are a compatibility
surface as real as the ABI**, so they are specified in this document and pinned
by tests rather than inherited from whatever is convenient to implement.

### Prosser's algorithm and "blue paint"

The formal model of macro replacement is Dave Prosser's, and its central device
is the **hide set**: each token carries the set of macro names (he writes `THS`)
that are not eligible to replace it, and expansion unions hide sets. "Painted
blue" is the informal name for a name in that state.

The standard's rule is per *macro*, per *scan*, not per token -- which is why
GCC can implement it with a disabled stack plus one flag. `minc+` follows the
stack model, and the reason is worth recording: a materialized hide set per
token makes the cost of a token proportional to the number of nested macros it
survived, which turns a pathological input (deeply nested expansion of a macro
whose name recurs) into quadratic memory. The stack gives the same answers with
bounded state. There is a test for exactly the case that separates the two
models (see "how the claims are checked").

### Rust, Swift, Zig -- and why `minc+` does not copy them

Rust's macro system is hygienic, AST-based and span-carrying; Swift's macros
operate on SwiftSyntax nodes; Zig's `comptime` sidesteps textual substitution
entirely. All three are better *macro systems*. None of them can `#include` a C
header, and every one of them has a C-interop escape hatch that has to
reimplement a textual preprocessor anyway. `minc+` is C-interop-first, so the
textual preprocessor is the load-bearing one; hygiene is worth stealing only as
an *optional* diagnostic (a macro that captures a name from its argument's
scope), never as a semantic change.

## The standard's contract, stated once

- **Phase 3** splits the source into preprocessing tokens and replaces comments
  with a space. `minc+`'s lexer already emits trivia, so this stage never
  tokenizes: it reads a token stream and *rewrites* it. The output keeps
  whitespace, because the tree above it is lossless and a tree cannot hold a
  byte that was thrown away here.
- **Phase 4** executes directives, then performs macro replacement *and
  rescanning*, repeatedly, until no macro name remains. A directive is a line
  whose first token is `#`; a `#` that is not the first token of a line is not a
  directive.
- **Rescanning is per macro replacement, and it never sees the rest of the
  file.** That is what makes `#define X X` terminate, and it is the rule the
  test in the previous section is about.
- **The translation limits are minima, not maxima**: C requires 15 nested
  `#include`s, 63 nested conditional inclusions, 127 parameters and 127
  arguments in one macro definition/invocation, 4095 simultaneously defined
  macro identifiers, 4095 characters in a logical source line, and 63
  significant characters in a macro name (C17 5.2.4.1). These are floors a
  conforming implementation must exceed, and they are the reason the bounds in
  this document are far larger than any real code needs.

## The design

### Where it sits

```
SourceFile ──▶ lex (lexOne per byte range) ──▶ TokenStream (lossless, trivia included)
                                                    │
                                                    ▼
                     pp: directives + macro expansion on tokens
                                                    │
                                ┌───────────────────┴───────────────────┐
                                ▼                                       ▼
              PPResult: preprocessed text + tokens            PPRecord
              + per-token origins + every lexed file   (definitions, includes,
                                │                          expansion map)
                                ▼                                       ▼
              lex::TokenStream (one unit, many files)           tools / LSP
                                │
                    ┌───────────┴───────────┐
                    ▼                       ▼
        parse::TokenSource            syntax tree builder
        (significant tokens)          (every token, incl. trivia)
                                │
                                ▼
                             parser
```

The preprocessor is a **client of the lexer**, not a stage before it. That is
Clang's arrangement and it is the only one that keeps one tokenizer: a macro body
is stored as tokens, a paste is re-lexed by the same `lexOne`, and there is no
second spelling of "what is an identifier". It also means the preprocessor never
sees a character that the lexer did not classify: `#` and `##` arrive as the
`Hash` and `HashHash` tokens of [`lexer.md`](lexer.md) (decision 13), and this
stage supplies the only thing the lexer could not — *position*. Being a client
is also what makes `mincc lex` meaningful on a real file: tokenizing does not
depend on directives existing, so a file full of them has no lexical errors in
it.

`pp` links `minc_lex` and `minc_span`, and **not** `minc_diag`: like the lexer
and the parser, it reports errors as values, and `minc_pp_report` is the separate
target that turns them into diagnostics. The tree/parser is *not* linked either
-- the preprocessor has no idea a parser exists.

### Pull, with a lazily-filled cache

The interface is a token cursor with lookahead, not a materialized vector:

```cpp
class PPTokenSource {
public:
  // The next token after expansions and directive evaluation.
  [[nodiscard]] PPToken next();
  // Lookahead without consuming. Any depth, because the pipeline is a cache.
  [[nodiscard]] const PPToken& peek(std::uint32_t ahead);
  void consume();
};
```

This is where `minc+` improves on both references. GCC's "backing up more than
one token is not permitted" is a real design constraint *of the token-list
model*; the pipeline here is a **cursor over a lazily-filled deque**, so
lookahead and pushback are the same operation and there is no backup problem at
all. Clang reaches the same freedom by different means (a lexer stack plus
`PeekAhead`, which is where OSS-Fuzz found a stack overflow in 2021 -- see
"Safety"). The deque has a cap; `peek` past the cap is a diagnostic, not
unbounded growth.

Only one thing is materialized: **the replacement list of the macro currently
being expanded**, plus its arguments, because the standard's rescanning rule is
defined over exactly that. That is the `ScratchBuffer` idea with an explicit
name, and it is bounded by the token budget.

### Expansion state: a context stack

```cpp
struct MacroContext {
  const MacroInfo* macro;        // nullptr for a directive-skipped region
  ExpansionFrameId frame;         // for provenance
  std::vector<PPToken> tokens;    // the replacement list, post-substitution
  std::size_t cursor = 0;
};

std::vector<MacroContext> contexts_;   // contexts_.back() is the innermost
```

`next()` takes a token from `contexts_.back()`; when a context is exhausted it is
popped (and the macro it belongs to is re-enabled). On `base context` the token
comes from the lexer. A macro name that is `enabled`, is not marked ineligible,
and is followed (after trivia) by `(` for a function-like macro, starts a new
context.

Three rules from GCC's writeup are adopted verbatim because they are the
subtle ones:

1. A macro is disabled **while its own replacement list is scanned** and
   re-enabled on pop; an argument's expansion happens with the macro *not*
   disabled.
2. The "is a `(` next?" test happens while the macro is disabled, and only then
   is the context pushed -- i.e. the parenthesis search never pops a context.
3. A token that did not expand because its macro was disabled is marked
   **ineligible for further replacement**, and that mark is the only per-token
   expansion state there is.

Rule 3 is the one that requires a per-token bit. It is carried in the token's
flags (the lexer's `TokenFlags` has room; this stage adds its own), so the
ineligibility mark costs no extra memory in the common case.

### Argument substitution

For a function-like macro with parameters `P1..Pn`:

1. Collect the arguments by scanning for top-level commas at depth 0 with
   respect to `(`/`)`, respecting string and char literals (the lexer already
   guarantees a literal is one token).
2. For each parameter, decide **once per definition** whether it appears as an
   operand of `#` or `##` anywhere in the replacement list. Substituting a
   parameter that is an operand of `#`/`##` uses the argument's **unexpanded**
   tokens, exactly as written; everywhere else the argument is **fully
   pre-expanded** first.
3. Substitute into the replacement list, then rescan it (which is what the
   context stack does -- no separate rescan pass).

The per-parameter `#`/`##` test is computed when the macro is defined and stored
in `MacroInfo`, so it is not re-derived per invocation. Both references do this;
it is worth stating because getting it wrong is the difference between
`paster(9)` working and not.

Variadic macros: `...` collects the tail, `__VA_ARGS__` names it. A function-like
macro invoked with no arguments where the definition has no `...` is an error;
invoked with `()` where `...` is the only parameter is **one empty argument**,
not zero arguments, which is the standard's rule and the source of the "detect
emptiness" folklore. C23's `__VA_OPT__(content)` expands to `content` when the
variadic part is non-empty and to nothing when it is empty; the GNU `, ##
__VA_ARGS__` comma-deletion extension is accepted **only** in GNU-extension mode
and diagnosed otherwise, because accepting it silently is how a header becomes
unportable.

### Stringifying and pasting: the only places tokens are synthesized

- `#param` stringifies the parameter's **unexpanded** tokens by re-spelling them
  from their source spans, with exactly one space between them where the
  original had whitespace, and escaping `"` and `\` inside string and char
  literals. The spelling is taken from the source bytes, not reconstructed from
  the token kind, so `1e10`, `0x1F` and `'x'` stringify as written.
- `a ## b` pastes the spellings of `a` and `b` and **re-lexes** the result with
  the same `lexOne`. A parameter that is an operand of `##` expands to its
  unexpanded argument; if the argument is empty, a **placemarker** token takes
  its place so the paste still has two operands (this is the standard's device,
  and both references implement it).
- If the pasted text is not a single preprocessing token, that is a
  **diagnostic**, not undefined behavior. Both GCC and Clang diagnose it; the
  standard calls it UB, and a language that targets production should report the
  thing that the user can fix. The message names both spellings.
- A pasted token's `TokenLoc` records **both** operand spans plus the `##`
  span, so a caret can show the two pieces that met.

The `#` at the start of a directive line is a different token from the `#` of
stringification; the lexer emits one `Hash`, and this stage decides which it is
by position. No lexer feedback, same principle as the parser's type positions.

### Directives

Implemented, with the semantics of C17 plus the C23 additions that are cheap and
already ubiquitous:

| Directive | Notes |
| --- | --- |
| `#define`, `#undef` | object-like, function-like, variadic; redefinition is diagnosed unless the replacement lists are **identical** (standard rule), and the `#undef`ed/`#define`d history is recorded for tooling |
| `#include`, `#include_next` | `"..."` searches the current file's directory first, `<...>` only the search list; both are ordered explicit lists (see below). The operand is a **header-name**, scanned from raw bytes -- see below |
| `#if`, `#ifdef`, `#ifndef`, `#elif`, `#elifdef`, `#elifndef`, `#else`, `#endif` | the skip stack is explicit; any directive other than a conditional is diagnosed inside a skipped region only for the conditions the standard requires |
| `#line` | accepted and validated; GNU line markers are **parsed** so that generated code can be consumed |
| `#error`, `#warning` | `#warning` is a diagnostic at warning severity, not an extension |
| `#pragma` | grammar defined, unknown pragmas **preserved** in the record and not diagnosed by default (`-Wunknown-pragmas` opt-in); `#pragma once` is honored |
| `_Pragma("...")` | the C99 operator form, registered as a builtin so the macro case works too: `#define PUSH _Pragma("...")` expands to the operator and rescanning meets it. It destringizes (`\"` to `"`, `\\` to `\`, and nothing else), lexes the result, and hands it to the same handler `#pragma` uses -- two spellings, one meaning. It emits no token, so nothing of it reaches the parser |
| `#` alone on a line | a null directive, as the standard says |
| `defined X` / `defined(X)` | an operator in `#if`, not a macro |

Reserved, with the decision recorded and the syntax *not* accepted yet:

- `#embed` (C23) -- accepted once it can be given the same bounds as `#include`
  (it reads bytes, so it gets the source-size limit and the same
  read-once identity rules). Not implemented before that, because "read a file
  into the token stream" without a byte budget is exactly the DoS the rest of
  this document is about.
- `#assert`/`#unassert` and GNU `#sccs`, `#ident`: rejected with a clear "not
  supported" rather than silently ignored.

### Conditional expressions

`#if` is evaluated over **preprocessing integers**, which are `intmax_t` /
`uintmax_t` -- there is no `int`/`long` question here. The evaluator:

- operates on 64-bit signed/unsigned values chosen by the standard's rules
  (unsigned if either operand is), so **no operation is undefined**: shift counts
  out of range are diagnosed, division by zero is an error, overflow is
  well-defined wrap;
- does not evaluate the *skipped* branch of `&&`/`||` for error purposes;
- expands macros first, except the operand of `defined`;
- treats an identifier that is not a macro as `0` (the standard's rule) and
  diagnoses it under `-Wundef`, which is the check that catches typos in
  `#if FEATURE_X`;
- is **shared with sema**: constant folding is one implementation used by both
  `#if` and, later, `const` evaluation. The interface is "evaluate this token
  sequence as an integer constant", and it lives in one file with two callers
  rather than being written twice.

### Header-names: the operand is not a token sequence

The operand of `#include` is a **header-name** (C 6.4.7), and the one thing that
matters about it is that it is not a sequence of ordinary tokens:

- `h-char` and `q-char` exclude only the newline and the closing delimiter, so
  `//` and `/*` are ordinary characters inside a name. Read as tokens,
  `#include <a//b.h>` becomes a line comment that swallows the `>`, and the
  directive is reported as an unterminated `<...>` -- a wrong diagnostic on a
  valid file;
- escapes do not exist there either, so reading `#include "c:\dir\x.h"` as a
  string literal draws "unknown escape" on a Windows path -- a *false* diagnostic
  on valid code, which is the worst kind;
- `>` is legal inside `"..."` and `"` is legal inside `<...>`, so no amount of
  joining tokens can express both.

The bytes are still there to read, which is why the token stream keeps trivia.
`lex::scanHeaderName` re-reads them from the opening delimiter, and the directive
line is rewritten so each operand is one `HeaderName` token. That is the same
move Clang makes from the other direction (`LexHeaderName`), and it is why the
scanner is a second entry point beside `lexOne` rather than a mode *inside* it:
`lexOne` stays a pure, restartable function of `(text, offset)` that knows
nothing about directives.

The consequence for diagnostics is explicit: the run records the span of every
header-name it read, and the lexical report skips any token that **begins**
inside one. Beginning rather than fitting, because the plain lexer's reading of
those bytes can run past the name -- `#include <a/*b.h>` is an unterminated block
comment that swallows the newline -- and the bytes past the name are re-lexed
rather than lost.

`__has_include(<name>)` goes through the same scanner, so the operator and the
directive cannot disagree about what a name is. A name produced by macro
expansion is not a header-name by the standard's rules (a header-name cannot be
formed by expansion); `<...>` from a macro is accepted anyway, as GCC accepts it,
by re-reading the bytes where the `<` was written.

### Include resolution

Search order is an explicit ordered list built by the driver and carried in
`PPOptions`; nothing is read from the environment (`CPATH`, `C_INCLUDE_PATH` and
friends are **not** consulted -- a build that depends on the machine's
environment is not reproducible):

1. for `"..."`: the directory of the including file (unless
   `-I-`-equivalent behavior is requested);
2. the `-I` list, in order;
3. the `-isystem` list, in order;
4. the built-in system list the driver passes for the target.

Each entry carries a `system` flag: diagnostics inside a system header are
suppressed unless enabled, which is market-standard behavior and the reason the
distinction exists.

**File identity.** `#pragma once` and the multiple-include optimization need to
know "have I already read *this* file", and a path string is not an identity:

- On POSIX the identity is `(st_dev, st_ino)`; on Windows it is the file index
  from `GetFileInformationByHandle`. Where neither is available, the fallback is
  a canonicalized absolute path with case folding applied exactly when the
  filesystem is case-insensitive.
- This matters concretely: on a case-insensitive filesystem (macOS, Windows)
  `Foo.h` and `foo.h` are one file, and an implementation that keys on the
  spelling will read one header twice and let two copies of an include guard
  macro fight. It also matters for symlinks (`a.h` → `b.h` → `a.h`), where the
  identity makes the cycle detectable and lets the error say **"a.h includes
  itself through b.h"** rather than the unhelpful "too deep".

**Multiple-include optimization.** When a file's first meaningful token sequence
is `#ifndef X` / `#define X` (or `#pragma once`) and the rest of the file is
inside that conditional, the file is recorded as guarded by `X`. A later
include of the same identity is skipped **without opening the file**, which is
what makes including a big header twice cheap. The pattern is only accepted in
the canonical form, because accepting near-misses is how a compiler creates a
heuristic that silently changes meaning.

**A missing guard is diagnosed.** If a file is included twice, was not skipped
by the optimization, and has no recognized guard, that is a warning naming the
file and the two include sites. No mainstream compiler diagnoses this, and it is
one of the most common real bugs in C code; the information is already in hand,
so reporting it is free. (It is a warning, not an error, because the second
inclusion is legal and sometimes intentional.)

**Read once.** A file's bytes are read once per compilation and cached by
identity. The compiler never re-opens a header to ask whether it changed: that
is a time-of-check/time-of-use hole, and it also makes the output depend on the
filesystem's state mid-run.

### The record: what the tools get

Two structures, both optional in the sense that the batch pipeline does not need
them and the driver asks for them:

```cpp
struct DirectiveRecord {
  SourceLoc span;          // the whole directive line
  DirectiveKind kind;      // Include, Define, Undef, Conditional, Pragma, ...
  SymId macro = kInvalidSym;   // for Define/Undef, the name
  std::uint32_t takeBranch;   // for conditionals: which branch was taken
};

struct InclusionRecord {
  SourceLoc directive;     // the #include
  support::FileId included; // the file it resolved to
  bool guardSkipped;        // true when the MI optimization elided it
};

// original → expanded, so an editor can answer "what did this expand to?"
struct ExpansionSite {
  SourceLoc invocation;
  std::uint32_t producedBegin;  // range in the emitted token stream
  std::uint32_t producedEnd;
};
```

The record is what makes these answerable without re-deriving anything:
go-to-definition on a macro, find-all-references, hover showing an expansion,
"which branch of this `#if` was taken and why", and the include graph that an
editor needs to invalidate the right files on save. It is also the input to the
`pp` command, so the feature is exercised by the compiler itself instead of
being tooling-only code that rots.

`ExpansionSite` ranges require recording during expansion, which costs; they are
produced only when `PPOptions::recordExpansionMap` is on (the `pp` command and
the LSP), and the frames used by diagnostics are always produced because a
diagnostic without them is worse than a slower compile.

### Reproducibility and determinism

The preprocessor is the stage where nondeterminism usually enters a build, so
the rules are explicit:

- `__DATE__` and `__TIME__` come from `SOURCE_DATE_EPOCH` when it is set, and are
  otherwise **an error** (not "now"), with the fix in the message. A build that
  silently embeds the current time cannot be reproduced; reproducible-builds.org
  exists because this is a real, common problem.
- `__FILE__` is the path as given to the compiler (the driver's job to make it
  relative to the build root when asked).
- `__LINE__` is the line of the invocation, not of the definition -- the classic
  bug, handled by treating it as a special macro expanded at invocation time.
- No clock reads, no environment reads beyond the explicit allowlist
  (`SOURCE_DATE_EPOCH`), no `getenv` in a header search, no dependence on the
  filesystem's iteration order, the locale, or the timezone.
- The output is a pure function of (file bytes, include search list, `-D`/`-U`
  list, options). A test asserts this by running the same input twice with the
  environment shuffled and diffing the token streams.

## Safety: every bound, and why each one exists

The threat model is the real one for a compiler: **input is untrusted**. Headers
come from third parties; a build system may compile code it did not write; an
editor will hand the front end a file that is being typed into. The second
threat is not an attacker at all: it is a macro library that is accidentally
exponential. Both have the same requirement -- the preprocessor must be **total**
-- and both have a public track record of failures:

- OSS-Fuzz has reported **stack overflow in `clang::Preprocessor`** more than
  once; the 2021 report is `Stack-overflow in clang::Preprocessor::PeekAhead`,
  i.e. in the lookahead path of the preprocessor itself. Recursion in this stage
  is not hypothetical.
- The classic macro bomb is exponential *by the standard's own rules*: with
  `#define A B B`, `#define B C C`, ... each level doubles the output. Blue paint
  stops only *direct* self-reference; it does not stop `A` expanding to `B B`.
  Any preprocessor that does not bound the result of expansion will consume
  unbounded memory on a 12-line file.
- Pasting is quadratic by construction if unbounded: each `##` re-lexes the
  concatenated spelling, so a growing token grows the work each round.

None of these are fixed by being careful. They are fixed by **budgets that are
always on**, each producing a named diagnostic:

| Hazard | Bound | Behavior on hit |
| --- | --- | --- |
| Direct or indirect recursion via `#include` | `kMaxIncludeDepth` (200; standard floor 15) | error naming the include chain; the file is abandoned, the TU continues |
| A conditional that never ends, or one nested past reason | `kMaxConditionalNesting` (256; standard floor 63) | error at the directive that exceeded it; the rest of the file is skipped to a matching `#endif` |
| Macro-on-stack recursion (`#define X Y` / `#define Y X`) | `kMaxExpansionDepth` (256) | error naming the macro chain |
| Exponential expansion, accidentally or not | `kMaxExpandedTokens` (8 Mi tokens per translation unit) | error naming the macro and the invocation that hit it; the budget is per TU, so the first flood reports once |
| Output larger than a source file should be | `kMaxPreprocessedBytes` (equal to `kMaxSourceBytes`, 64 MiB) | same error family, checked before the buffer grows |
| Unbounded pasting | `kMaxTokenBytes` (4095; standard floor for a logical line) | error naming both operands |
| A macro with a silly parameter list | `kMaxMacroParameters` (256; standard floor 127) | error at the definition |
| The same header included a million times | `kMaxIncludesPerUnit` (65536) | error naming the file |
| Lookahead past the pipeline cache | `kMaxLookahead` (64) | error: no token sequence in the language needs it |
| A diagnostic flood | reuse `kMaxDiagnostics` | the bag's existing cap and its suppressed-count summary |

Every one of these lives in `support/limits.h` with the rest, and every one is
**tested by a case that is expected to diagnose** rather than to crash, hang, or
allocate. That is the difference between a bound and a comment.

Three properties make the bounds trustworthy rather than merely present:

- **They are checked before the allocation, not after.** `kMaxExpandedTokens` is
  enforced as tokens are appended, so the array cannot grow past it; the
  arena/source limits already work this way.
- **Hitting one produces a diagnostic and a defined state**, not a partial silent
  output: the tokens produced so far are still a valid stream that covers
  everything read so far, so the parser and every tool see a consistent prefix
  plus an error. (This mirrors the parser's bail-out: the tree after giving up
  still covers every byte.)
- **There is no configuration that removes them.** They can be raised, never
  disabled. A "no limits" switch would be a switch that turns a compiler into a
  denial-of-service tool.

### The untrusted-input promise, stated

For any byte sequence, the preprocessor terminates, and it either produces a
token stream or a diagnostic; it never crashes, hangs, reads outside the include
search list, or allocates more than the budgets above. Supporting decisions:

- **No global state, no statics, no singletons.** One `Preprocessor` per
  `Session`; every buffer owned; the whole thing is reentrant. A preprocessor
  with a static scratch buffer is both a threading bug and an information leak
  between compilations (the LSP runs several).
- **No recursion without a guard**, exactly as in the parser: the expander's
  recursion is the context stack (explicit), the conditional nesting is a vector,
  and the include stack is a vector. The only recursive function is `#if`
  evaluation, which takes a depth guard.
- **Filesystem access is confined** to the include search list plus the input
  file. `#include "/etc/passwd"` is legal C and stays legal -- the protection is
  that the path is resolved, recorded and bounded, not that it is forbidden.
- **The lexer's validation boundary is reused.** A header goes through
  `SourceManager::addFile`/`loadFromDisk`, so it is size-limited, UTF-8-validated,
  BOM-stripped and NUL-rejected before this stage sees it. The preprocessor does
  not add a second file-reading path.

## Limits

New limits, all in `support/limits.h`:

| Constant | Value | Enforced by |
| --- | --- | --- |
| `kMaxIncludeDepth` | 200 | `IncludeResolver` (per-TU include stack) |
| `kMaxConditionalNesting` | 256 | `Conditionals` (skip stack) |
| `kMaxExpansionDepth` | 256 | `Expander` (context stack) |
| `kMaxExpandedTokens` | 8 Mi | `Expander` token budget |
| `kMaxPreprocessedBytes` | 64 MiB | `PPTokenSource` output budget |
| `kMaxTokenBytes` | 4095 | `Stringify` (paste/stringify result) |
| `kMaxMacroParameters` | 256 | `Directive` (`#define`) |
| `kMaxIncludesPerUnit` | 65536 | `IncludeResolver` |
| `kMaxLookahead` | 64 | `PPTokenSource::peek` |

Each one has a `static_assert` or a test that pins the relationship between the
number and the behavior, in the same spirit as the existing source/arena limits.

## Layers and files in `src/pp`

No god-files; each file is one responsibility, and the split follows the seams
where behavior is testable in isolation.

| File | Responsibility |
| --- | --- |
| `pp_token.h` | `PPToken`, `TokenLoc`, `SourceLoc`, `ExpansionId`, and the token flags this stage adds |
| `expansion_table.{h,cc}` | hash-consed `ExpansionFrame` table, frame chains, backtrace generation |
| `macro.h`, `macro_table.{h,cc}` | `MacroInfo` (kind, parameters, `#`/`##` operand flags, replacement tokens, definition site), define/undef, identical-redefinition check, history |
| `directive.{h,cc}` | directive lexing and dispatch: one function per directive, one table |
| `conditionals.{h,cc}` | the `#if` family, the skip stack, branch-taken decisions, `#elifdef` |
| `const_expr.{h,cc}` | the preprocessing integer evaluator (shared with sema later) |
| `expander.{h,cc}` | the context stack, invocation detection, argument collection, substitution, rescanning, the "not available for further replacement" mark, budgets |
| `stringify.{h,cc}` | `#` spelling and `##` pasting, placemarkers, re-lexing via `lexOne` |
| `include_resolver.{h,cc}` | search lists, `""`/`<>`, `#include_next`, file identity, `#pragma once`, multiple-include optimization, include stack, `InclusionRecord`s |
| `builtins.{h,cc}` | `__FILE__`/`__LINE__`/`__COUNTER__`/`__has_include`/`__DATE__`/`__TIME__` and the reproducibility gate |
| `pp_token_source.{h,cc}` | the pull interface, the lazily-filled cache, and the adapter to `parse::TokenSource` |
| `pp_record.{h,cc}` | `DirectiveRecord`, `InclusionRecord`, `ExpansionSite`, and the expansion map |
| `pp_error.{h,cc}` | the closed error-code set and the error value (the same shape as the lexer's flags and the parser's codes) |
| `preprocessor.{h,cc}` | the facade: owns the state, sequences a translation unit, enforces the budgets |
| `pp_report.{h,cc}` | errors → diagnostics; the only file here that knows about `Span`, severity and `DiagBag` |

Plus one new support leaf, `src/support/fs`: canonicalization and file identity
(`(device, inode)` / file index, with a canonical-path fallback). It is
platform-specific code, so -- like `support/term` -- it is confined to one
module and everything else asks it a yes/no question. It is needed by the
multiple-include optimization, by `#pragma once`, and later by the language
server's file watching, so it belongs in `support`, not in `pp`.

## The `pp` command

```
$ mincc pp examples/001_main_func.mx            # the token stream the parser sees
$ mincc pp --at examples/004_operators.mx:12    # how line 12 expanded, step by step
$ mincc pp --defines examples/004_operators.mx   # what was defined, where, and whether used
$ mincc pp --includes examples/001_main_func.mx  # the include graph, and what was guard-skipped
$ mincc pp --deps examples/001_main_func.mx      # a Make-style dependency line
$ mincc pp -DMAX=10 file.mx                      # predefine, as the driver would
```

Every mode prints provenance: `--at` walks the expansion frames, `--defines`
reports definition sites and use counts, `--includes` shows which includes were
elided by the guard optimization. No extra commands beyond these, and none of
them exists before the stage they describe (`docs/roadmap.md`).

The default mode prints the significant tokens of the translation unit -- the
ones the parser reads -- because that is what a reader means by "the output".
Trivia is in the stream, but printing it would double the length of the table
without answering anything; `mincc parse` is where whitespace is visible.

Lexical errors are reported for **every file the run read**, not just the one
named on the command line: the preprocessor is the only stage that knows a
header was opened, so it is the only stage that can report a bad byte in one.
The `Hash` and `HashHash` tokens are the one thing filtered out of that report,
not because they are questionable but because they are already correct tokens:
whether a `#` sits at the start of a line is a fact this stage owns and the
lexical pass cannot see, so `pp_report` leaves them to the code that decides it
(the filter, and the claim, live in `pp_report`).

A `#` that starts no directive and a `##` outside a macro body are the
preprocessor's own error, `pp-stray-hash`, reported once with the caret on the
operator. The token is still emitted, so the stream stays lossless and the
tree the parser builds from it still contains every byte.

`mincc lex` reports no preprocessing errors because it does no preprocessing:
its job is the lexical grammar, and `#` is part of the lexical grammar. `mincc
parse` runs the whole front end (`source -> lex -> preprocess -> parse`), so a
file with directives has a tree; `mincc pp` is the token-level view of the same
unit; `mincc lex` is the
stage-level view of one file.

## How the claims above are checked

| Claim | Checked by |
| --- | --- |
| Macro replacement matches the standard | a corpus per rule: rescanning, blue paint, the `foo(foo) (2)` case, `#`/`##` operand rules, placemarkers, empty arguments, `__VA_OPT__`, `defined`, nested conditionals |
| ...and matches the market | **not yet run**: a differential test against the system preprocessor (`clang -E` for the C-like cases, `gcc -E` for the GNU ones) over a macro-only corpus. The individual rules are pinned by hand instead; this is the harness that would catch the ones nobody thought to write down |
| Expansion terminates | a bomb corpus (`A → B B`, nested `##`, self-referential guards) where every case must diagnose within a budgeted time |
| The bounds are bounds | one case per limit that must produce its diagnostic, and a test that the budget is checked *before* the allocation (a hostile input cannot make the process allocate past it) |
| No recursion without a guard | deeply nested `#if`, deep `#include` chains, deep macro recursion, run under the sanitizer preset |
| Provenance is real | for every emitted token: its `spelling` points at bytes that exist, and re-lexing that span yields the same kind; for every diagnostic: walking the frame chain terminates and reaches a real invocation site |
| Determinism | the same input preprocessed twice with a shuffled environment and a different `TZ`/locale produces byte-identical token streams; a build with `__DATE__`/`__TIME__` and no `SOURCE_DATE_EPOCH` fails with that diagnostic |
| File identity is identity | the same header reachable through a symlink, a relative path, a `..` path and (where the filesystem allows it) a different case is read **once**; a self-including file reports the cycle by name |
| The guard optimization is safe | a guarded header included twice produces the same output as with the optimization disabled (the test runs both and diffs) |
| The record is complete | every directive in the corpus appears in the record with its span and kind; every expansion site's recorded range maps back to the frame it came from |

The differential test is the strongest of these and the one most worth the
effort: it is what catches "we implemented what we thought the standard said"
in the corners that no one reads, and it is cheap because `cc -E` and
`clang -E` are already on the machine in CI. It is the one row in that table
without a check behind it, and the honest reading of this document is that the
rules it *does* claim are verified individually rather than in bulk.

## What the implementation corrected

Wiring the stage into the front end is what proves it, and doing so corrected
two decisions in this document. Both are recorded here rather than silently
edited, because the reason each was wrong is the interesting part.

1. **The output is text, not a token list, and trivia is part of it.** The
   design said the parser consumes "the significant tokens" and that trivia was
   "a filter over the token stream". That is half true: the *parser* is
   trivia-blind, but the tree builder above it is not -- it is the component
   that holds every byte, and it reads the same stream. Dropping trivia here
   left the tree over a preprocessed file unable to hold a single space, and
   `SyntaxTree::lossless`, `reconstruct()` and the formatter all rest on
   holding every byte. So `PPResult` now carries the preprocessed **text** and
   the tokens that tile it, and both consumers read one thing.
2. **A tree over a preprocessed unit points into several files.** Lean
   provenance was designed as "a span per token that names its spelling site",
   and that is what it is -- but it also means a `lex::TokenStream` can no
   longer assume one `FileId` for every token. `fromPreprocessed` carries an
   origin per token, `TokenStreamSource` asks for it, and the *tree* stays
   single-unit (its text is the preprocessed text) while a caret still points
   at the header the bytes were written in.

Two rules fell out of (1) and are now load-bearing:

- **The separator rule.** Two tokens are separated by one space exactly when the
  second does not continue the previous bytes verbatim, decided from the two
  origins. A file with no directives therefore preprocesses to bytes identical
  to its input -- which is why every existing tree test still passes unchanged --
  while a macro's replacement gets the space it needs because nothing was
  written there to copy. Trivia written in a file is copied verbatim; trivia
  inside a replacement list is dropped, because copying it would make the output
  depend on how a macro happened to be formatted.
- **The lifetime rule.** A leaf's text is a view into the preprocessed text, and
  the node cache is shared across inputs, so the text must outlive the cache.
  Freeing a `PPResult` at the end of the iteration that produced it is a
  use-after-free that the sanitizer preset caught on the first multi-file run;
  the driver now keeps every result alive for the invocation, and `reserve` on
  that vector is load-bearing because a reallocation would move the bytes out
  from under the views.

## Non-goals

- **Not a macro system.** No hygiene, no pattern matching, no `$`-splicing. C
  macros are textual and stay textual; hygiene is only ever a warning.
- **Not a linker or a module system.** `#include` is file inclusion; C++20-style
  modules and header units are a later, separate design.
- **Not a build system.** No dependency generation beyond the `--deps` line,
  no caching to disk, no PCH. A precompiled preamble for the language server is
  a plausible later stage and the record is shaped for it, but the format is not
  designed here.
- **No new file-reading path.** Everything goes through `SourceManager`.
- **No `#pragma` implementation.** Pragmas are parsed, preserved and reported;
  interpreting them is each target's business, and pretending otherwise is how
  compilers grow piles of vendor-specific state.

## Decisions, now fixed

| # | Decision | Choice |
| --- | --- | --- |
| 1 | Where it runs | On the token stream, as a client of the lexer; `#` belongs to this stage |
| 2 | Pull vs materialize | Pull, over a lazily-filled cached cursor; only the current macro's replacement list is materialized |
| 3 | Lookahead | Arbitrary and cheap (a cache, not a backup); capped at `kMaxLookahead` |
| 4 | Expansion state | A context stack (GCC's model), plus one per-token "ineligible" bit |
| 5 | Provenance | `TokenLoc { spelling, expansion }` + a hash-consed `ExpansionTable`; never compressed into one integer |
| 6 | Synthesized tokens | Only `#` and `##`; both record their operands' spans and the operator's span |
| 7 | Invalid paste | A diagnostic, never UB |
| 8 | Argument expansion | Pre-expanded except where the parameter is an operand of `#`/`##`, decided once per definition |
| 9 | `__VA_OPT__` | Implemented (C23); `, ## __VA_ARGS__` only in GNU-extension mode |
| 10 | `#if` arithmetic | 64-bit `intmax_t`/`uintmax_t`, no UB, division by zero diagnosed, shared with sema's constant folding |
| 11 | Include identity | `(device, inode)` / Windows file index, canonical-path fallback; cycles reported by name |
| 12 | Include search | Explicit ordered lists from the driver, `system` flags, **no environment variables** |
| 13 | Missing include guard | Diagnosed (warning) when a file is read twice without a guard |
| 14 | Multiple-include optimization | Canonical guard patterns and `#pragma once` only; asserted equivalent to no optimization |
| 15 | `__DATE__`/`__TIME__` | `SOURCE_DATE_EPOCH` or an error; never the clock |
| 16 | Bounds | The nine in the limits table; always on, raisable, never removable; each with a code and a test |
| 17 | Errors | Values, with a closed code set; `minc_pp` links no diagnostics, `minc_pp_report` does |
| 18 | State | One `Preprocessor` per `Session`; no globals, no statics, reentrant |
| 19 | Tooling information | A record (definitions, includes, branch decisions, expansion sites), always for diagnostics, optionally for the expansion map |
| 20 | Reserved syntax | `#embed` and `#pragma` semantics recorded, not accepted until bounded; unknown directives are errors |
| 21 | Header-names | Scanned from raw bytes by `lex::scanHeaderName`, one `HeaderName` token per operand, spliced in before a directive is handled. A header-name's bytes are *not* the tokens the plain lexer made of them, so the run records its spans and the lexical report skips what begins inside one. `#include` and `__has_include` go through the same scanner, so they cannot disagree about what a name is |
| 22 | `_Pragma` | A builtin, not a scanner special case: post-expansion handling is the only way the `#define PUSH _Pragma("...")` form can work, and one handler shared with `#pragma` is the only way the two spellings can mean one thing |
